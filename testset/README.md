# Тестовый набор: запросы и правильные ответы

Набор нужен, чтобы проверять любое решение — наш план, Elasticsearch, Meilisearch и т. д. — на одних и
тех же запросах с заранее записанными правильными ответами.

## Что внутри

Каждый набор — JSON-файл в `suites/`: корпус (клиенты и документы в модели данных из задания), запросы с
правильными ответами и иногда проверки HTTP-контракта. Читаемая версия каждого набора, где вместо
идентификаторов стоят имена клиентов и заголовки документов, лежит в `lists/`.

Наборы трёх происхождений:

- **Написаны вслепую** (`codex-*`, `claude-*`). Агенты Codex (GPT-6) и Claude Opus 5.5 получили одно и
  то же задание по трём темам — клиенты, документы, смешанные случаи — и придумали корпус, запросы и
  правильные ответы, не видя ни плана, ни работ друг друга. Задания лежат в `research/testgen/`.
- **Из исследования** (`existing-*`, `tools-mini-6`): наборы, на которых измерялись решения плана и
  сравнивались готовые инструменты.
- **Из открытых датасетов** (`ds-*`). Правильные ответы получены механически: из разметки самого датасета
  (ключ ответов, кластеры, типы документов, оценки людей) и, для запросов о назначении документа, из
  официальных британских перечней (GOV.UK) с цитатой. Скрипт сборки каждого набора лежит в
  `research/datasets/build/`, использованный фрагмент данных — в `research/datasets/raw/`. Источник,
  версия и атрибуция записаны в полях `about` и `source` набора.

## Формат запроса

| Поле | Смысл |
|---|---|
| `q` | текст запроса |
| `level` | `required` — следует прямо из текста задания; `expected` — этого ждал бы разумный проверяющий; `nice` — желательно, провал не дефект |
| `category` | тип случая: e-mail, порядок имён, опечатка, понятие, идентификатор, мусор и т. д. |
| `scope` | какие результаты оцениваются: `all` (по умолчанию), `clients` или `documents` |
| `relevant` | что правильный поиск должен вернуть |
| `acceptable` | что можно вернуть без штрафа |
| `others` | `wrong` (по умолчанию) — любой результат вне `relevant` и `acceptable` считается ошибкой; `ignore` — прочие результаты не оцениваются |
| `must_not` | что возвращать нельзя |
| `first` | кто из результатов должен стоять первым |
| `top_set` | какие результаты должны занять первые места, в любом порядке |
| `before` | пары `[a, b]`: оба есть в выдаче, и `a` стоит выше `b` |
| `within_top` | для опечаток: хватит, чтобы хотя бы один из `relevant` был в первых k результатах |
| `min_results` | минимальное число результатов |
| `empty` | правильный ответ — пустой список |
| `why` | почему ответ именно такой |

Проверки HTTP-контракта (`http_cases`): метод, путь, параметры, тело и список кодов ответа, каждый из
которых считается правильным.

## Как засчитывается ответ

На вход подаётся упорядоченный список того, что вернул поиск. Сначала из него убираются результаты вне
`scope`. Запрос засчитан, если выполнены все применимые условия:

1. `empty`: список пуст.
2. `relevant`: все перечисленные есть в списке; при `within_top` — хотя бы один в первых k. Если выдача
   собиралась с лимитом N, а правильных ответов больше N, достаточно N правильных (`--limit N`).
3. `others: wrong`: в списке нет ничего, кроме `relevant` и `acceptable`.
4. `must_not`: ничего из перечисленного в списке нет.
5. `first`: первый результат входит в `first`.
6. `top_set`: первые места заняты ровно этими результатами.
7. `before`: для каждой пары оба результата есть и первый стоит выше.
8. `min_results`: результатов не меньше указанного.

Итог считается отдельно по уровням (`required`, `expected`, `nice`) и по категориям.

## Как пользоваться

```
python3 validate.py suites/*.json              # формат и ссылки на корпус
python3 render.py suites/*.json                # читаемые списки в lists/
python3 score.py suites/X.json results.json    # оценка; results.json = {"q001": ["c01", "d03", ...], ...}
python3 score.py suites/X.json --oracle        # самопроверка: идеальная выдача проходит все проверки
python3 score.py suites/X.json results.json --limit 50   # если выдача собиралась с лимитом 50
```

Выдачу стоит собирать с лимитом 50 — это максимум в плане API. Часть запросов ждёт больше 10 результатов:
например, на `address proof` в `ds-sinabis-docs` 60 правильных документов, а короткие запросы вроде `a`
в `existing-clients-fixture-42` должны вернуть не меньше 20 клиентов.

Скрипты используют только стандартную библиотеку (Python 3.10+). Загрузчика, который заливает корпус в
работающий API и сам собирает `results.json`, пока нет: он появится вместе с реализацией. Идентификаторы
сервера надо сопоставить идентификаторам набора при загрузке корпуса.

Все наборы проходят самопроверку `--oracle --limit 50`, то есть ожидания внутри каждого набора не
противоречат друг другу и выполнимы при лимите 50.

## Оговорки

- Наборы `codex-*`, `claude-*` и `existing-*` целиком написаны языковыми моделями: и тексты, и правильные
  ответы. Наборы `ds-*` взяты из датасетов. Разметка в них частично человеческая: оценки FiQA, классы
  RVL-CDIP, ключ ответов Senzing. В остальных она синтетическая или собрана механически.
- В `ds-enron-emails`, `ds-opensanctions-names` и `ds-rvlcdip-types` настоящие данные: переписка
  сотрудников Enron, британский санкционный список, сканы документов табачной отрасли. Остальные корпуса
  синтетические.
- Авторы судили о релевантности независимо, и в спорных местах их решения расходятся. Пример:
  `codex-mixed` считает, что пустой запрос должен давать `200` и `[]`, `claude-mixed` — `400` или `422`, наш
  план — `422`.
  Расхождения не сведены, поэтому провал на уровне `nice` или в спорной категории не обязательно означает
  дефект.
- Официальные перечни документов тоже расходятся. Страница GOV.UK о пособии JSA принимает расчётный
  листок как подтверждение адреса, а в перечне Bona Vacantia его нет; Bona Vacantia прямо отказывается
  принимать выписку по кредитной карте. Наборы `ds-*` указывают, на какой перечень опирается каждый ответ.
- `existing-clients-fixture-42` написал автор эталонного SQL, а `tools-mini-6` — автор плана, поэтому эти
  два набора не независимы от плана.
- `existing-documents-86` разделён на `dev` (подбор порогов) и `test` (итоговые цифры). Подбирать
  параметры по `test` нельзя.
- В `ds-fiqa` и `ds-enron-emails` размечены не все тексты: неразмеченный текст может оказаться полезным.
  Поэтому там прочие результаты не оцениваются (`others: ignore`), а для вопросов Enron достаточно найти
  исходное письмо в первых пяти.
